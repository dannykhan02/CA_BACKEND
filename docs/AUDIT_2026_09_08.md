**AI cost and model routing**

The five document analysis calls each send up to 60,000 characters of extracted_text, not 60,000 tokens. Summary uses previously extracted structured JSON; Q&A uses retrieved context. They should not be counted as additional identical full-document calls. There is no cache_control in AnthropicClient.

Prompt caching is feasible, but simply marking the existing document text is insufficient: each current template starts with different task instructions, and cache identity includes the entire preceding prefix. Refactor into a common trusted framing plus a byte-identical document content block with an explicit breakpoint, followed by purpose-specific instructions and output schema. Keep sensitivity/task metadata that differs between calls after the breakpoint. Version the affected templates; PromptManager currently renders one flat string, so introduce a block-oriented request/rendering interface. Preserve untrusted-document framing.

Anthropic documents full-prefix caching, a 4,096-token minimum for Haiku 4.5, a default five-minute TTL, and availability only after the first response begins. The initial four-job batch runs concurrently, so stage one request first before dispatching the other consumers if deterministic cache hits are desired. Account for queue delays; routing to different models needs separate cache populations. Record cache_creation_input_tokens and cache_read_input_tokens, currently discarded. Source: [Anthropic prompt caching documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Illustrative estimate, not measured savings: at the documented Haiku 4.5 input prices, for a shared D-token prefix, five ordinary inputs cost 5D units; a five-minute cache write plus four hits costs (1.25 + 4×0.10)D = 1.65D, a 67% reduction on that shared input. At an assumed 15,000 shared tokens this is $0.075 versus $0.02475 per document. With a one-hour write the equivalent is 2.4D, or 52% less. Task instructions, output tokens, retries, short documents, cold concurrent requests, and cache expiry reduce total savings. These are derived estimates using the same [Anthropic pricing table](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Estimated implementation scope: 2–4 engineering days for shared request blocks, five template versions, orchestration, cache usage columns/telemetry and HTTP-fake regression tests, plus representative-document quality validation. This is a planning estimate, not a delivery commitment.

**P2 — ai_prompts.model is ignored.** `app/Services/AnthropicClient.php:174` always sends config('services.anthropic.model'); recordAiRun and downstream result writers likewise record the global model. Current effective model is Haiku 4.5 for classification, entities, risks, deadlines, insights, summary, Q&A, and Claude vision OCR. The row's provider, temperature, and system_prompt are also not honored. Introduce resolved request options, use the row model with explicit global fallback, and propagate the actual response model into provenance. Classification/simple extraction can remain on Haiku; evaluate a stronger model for ambiguous risks/insights using labeled examples. There is no present per-purpose routing, and switching to the existing row values alone saves nothing because all equal the global model. Estimated routing change: roughly 1–2 days plus quality evaluation.

**Structured numeric extraction is available for DOCX/spreadsheets; PDF needs reconstruction.** `DocumentTextExtractor.php:92` already traverses PhpWord Table→Row→Cell, then reduces rows to pipe-delimited text. It does not omit tables entirely, but discards the table object structure and source-cell metadata. Preserve tables alongside text and derive candidate numeric facts with row/column headers, units, periods, and cell provenance. SpreadsheetTextExtractor.php:16 has sheet arrays available but stringifies them; preserve raw/formatted values and coordinates. Those formats offer the lowest-cost deterministic path.

Smalot PDFParser currently ends at parseFile()->getText(). The installed library exposes Page::getDataTm(), getTextXY(), and getTextArray(), so positioning is available and currently unused. These are not a ready-made semantic table grid: columns, merged cells, headers, and multipage tables require reconstruction or another extractor. Tesseract similarly discards TSV geometry when joining words. Do not claim arbitrary PDF numbers can be safely mapped to KPIs without that work. Start with DOCX/spreadsheet evidence candidates, ask AI to select/describe evidence rather than retype numbers, and validate numeric outputs against source facts. Estimated structured DOCX/spreadsheet foundation: 3–5 days; PDF table quality needs a separate sample-driven spike.

**Pipeline robustness**

**P1 — An attempted AI run is incorrectly treated as committed success.** AnthropicClient records DocumentAiRun immediately after the HTTP result and before JSON decoding/validation (e.g. lines 43–45). Each job persists results later. SkipsUnchangedDocuments.php:40 checks only the latest document/purpose file hash; it checks neither successful validation nor committed outputs, prompt/model version, or changed extracted text.

Concrete failure: insights receives valid JSON with data that fails a database constraint. The AI run is already committed; the result transaction rolls back and status remains Processing. On automatic retry, GenerateInsightsJob.php:50 sees the matching hash, skips Claude, and writes Ready/100 despite no newly committed results. A timeout between AI-run insertion and persistence has the same risk. Invalid JSON can also poison the guard, though the caught error explicitly fails that attempt. On a completely new document with no matching historical run, the guard cannot skip: this does not prove zero historical Claude calls. It does prove Ready without a successful result or a fresh retry call.

Manual AI-only reprocessing passes forceReprocess=true. Full scan/extraction reprocessing in DocumentReprocessController.php:35 does not pass it, and DispatchesIntelligenceChain constructs jobs with default false. Thus manual reprocessing does not universally bypass the guard. Summary's input is upstream structured data, so file hash alone is especially unsuitable when upstream results change.

Fix: separate usage/attempt accounting from successful stage completion. Commit validated outputs and a success marker atomically, with a processing-generation ID plus text/input digest, purpose, prompt version, and actual model. Skip only a matching successful generation. Preserve legitimate empty results via explicit success metadata. Propagate force consistently and reject stale-generation writes.

**P1 — AI timeouts cannot accommodate retry budgets.** Effective HTTP timeout is 60 seconds. Four total attempts (initial plus three retries) with 2+4+8-second sleeps permit 254 seconds, plus up to 20 seconds of local throttling. Positive Retry-After values have no cap, so the actual bound is unbounded. Job tries does not multiply a job's allowed execution time. Installed Laravel Worker::timeoutForJob uses the job timeout in preference to the supervisor timeout.

| Job | Tries | Timeout seconds | Assessment |
| --- | --- | --- | --- |
| ClassifyDocumentTypeJob | 2 | 60 | Even one 60-second HTTP attempt leaves no overhead; retries cannot fit |
| ExtractDocumentEntitiesJob | 2 | 60 | Same |
| DetectDocumentRisksJob | 2 | 60 | Same |
| DetectDocumentDeadlinesJob | 2 | 60 | Same |
| GenerateDocumentSummaryJob | 2 | 60 | Same |
| GenerateInsightsJob | 2 | 120 | Less than the 254–274-second retry budget |
| OcrPageBatchJob | 2 | 90 | Three sequential Claude calls can require 762 seconds plus throttling; Tesseract allows 60 seconds per page, also exceeding 90 in aggregate |
| GenerateEmbeddingsJob | 2 | 90 | Single Voyage HTTP timeout is 30 seconds; no analogous nested retry mismatch, but chunking/database writes remain unbounded by workload |
| ExtractDocumentTextJob | 2 | 120 | Rasterizer allows 60 seconds; download/native parsing/DB work have no guaranteed total bound |
| ScanUploadedFileJob | 2 | 60 | Connect is 5 seconds and socket inactivity timeout 30 seconds; download and repeated writes are not a total 60-second bound |

Redis retry_after=150 currently exceeds the longest job timeout=120; that relationship is presently reasonable and must change if job timeouts increase. Horizon extraction timeout=150 does not override the shorter explicit job limits. Most AI handlers catch errors and call $this->fail(), making those errors terminal immediately despite tries=2. Embedding provider errors are swallowed after marking the stage failed. Hard timeouts may leave processing_jobs records in running state because failed() usually only logs or updates document status.

Prefer one bounded HTTP attempt per queue execution, release/retry with bounded backoff, and explicit terminal-vs-retryable exceptions. Otherwise cap Retry-After and align HTTP/retry/job/Horizon/reservation budgets coherently. Include tests for timeout after usage insertion and before result commit.

**P1 — Ready does not certify complete analysis or human approval.** Insights sets Ready inside its own result transaction, independently of the parallel intelligence batch. That batch permits failures, and finally dispatches summary even when siblings failed. Summary can contain empty or stale categories without signaling incompleteness. Normal successful processing never requires human approval; DocumentApproveController merely changes Needs Review to Ready without requiring successful AI stages or scheduling missing ones. If the stated pipeline requires review before export, a separate approval state and export gate are needed.

**The normal KPI/chart/insight write transaction is sound, but bypass paths are not.** GenerateInsightsJob.php:87 replaces KPIs/charts/points and writes document insights/Ready in one DB transaction, so a normal failed insert does not commit a half-written set. However the precommitted AI run makes its retry unsafe, as above. ResponseValidator::validate also allows missing fields; a decoded empty object passes and becomes three empty arrays, replacing previous data and marking Ready. This was reproduced by calling the validator locally. Require the entire envelope and validate nested KPI/chart/point values. An intentionally empty narrative result can remain valid when explicitly returned.

GenerateEmbeddingsJob writes replacement chunks transactionally and never changes document status; Ready with absent embeddings is intentional. It runs after insights on the upload chain, not after all intelligence jobs. AI-only manual reprocess does not dispatch embeddings at all, allowing stale/missing search data to persist. Validate vector count/dimensions and index alignment before replacement, track search readiness separately, and schedule refresh after successful reprocessing if required. No generation lock protects either job against older queued work overwriting newer processing state.

**P1 — Scanner accepts an empty/unrecognized clamd reply as clean.** ScanUploadedFileJob.php:105 rejects only false or a response containing ERROR, then classifies everything without FOUND as OK. An EOF returning an empty string therefore passes the scan. Require an explicit valid clean response, check socket timeout and write completion, and treat malformed/empty replies as scanner failure. This is a source-level finding, not a live malware/scanner experiment.

**P1 — Direct table reads bypass reporting eligibility.** The RLS migration grants SELECT on all columns of four base tables because the views are security_invoker. Their policies restrict workspace only. A future mapped reader can SELECT its own Restricted documents, extracted_text, and non-Ready results directly, ignoring the view predicates. This is an intra-workspace confidentiality/reporting-boundary defect, not demonstrated cross-workspace leakage. Add eligibility restrictions to all reachable document/child policies or publish a separately owned reporting surface with deliberately restricted columns and a carefully verified tenant identity boundary.

**P1 — Soft-deleted documents remain in reporting views.** Both live definitions filter classification != Restricted and status=Ready but omit deleted_at IS NULL. Eloquent soft-delete scopes do not apply to PostgreSQL views. A Ready document deleted in the app retains its children and continues to qualify for BI. Fix both views and direct-table policies; verify with a deleted Ready fixture in an isolated PostgreSQL test database.

Neither view gates on human approval or powerbi_enabled. Approval is not separately represented by Ready. The app/table owner bypasses RLS (FORCE ROW LEVEL SECURITY is false), so using application credentials in a BI connection would defeat the intended tenant boundary. No live BI connection was inspected.

Additional operational defect: CreatePowerBiReader derives role names from workspace names, allowing collisions and PostgreSQL identifier truncation; creation/grant/mapping are separate statements. The documented revoke-then-create rotation is broken: revoke retains the mapping row, then create uses PowerBiCredential::create with the same unique db_role. Role creation/grant can succeed before that insert fails, leaving an unmapped role. Prefer stable UUID-based names and transactional provisioning/rotation.
