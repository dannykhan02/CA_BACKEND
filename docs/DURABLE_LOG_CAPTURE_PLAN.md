# Durable log capture — top remaining Tier 1 priority

Status: proposal only, 2026-09-14. No logging configuration, vendor account, Railway service, token, deployment or alert has been changed. The September 13 incident's Railway logs are confirmed unrecoverable. Durable capture takes priority over the older Tier 1 ordering; the pooling investigation remains a separate evidence task.

## Decision proposed

Use **structured stdout/stderr plus an explicit forwarder to an external managed log service**, provisionally Better Stack. Require **at least 30 days searchable retention**; price 90 days before choosing retention. Preserve environment/service/replica/deployment identity and exception chains. Keep Sentry for error investigation alongside the log stream.

Railway captures stdout/stderr and supports JSON logs, but currently documents **no native log-drain setting**. Its retention is plan-dependent (Free 3 days, Hobby/Trial 7, Pro 30, Enterprise up to 90). Increasing Railway retention alone does not create an independently retained external copy. These are future-design facts, not a request to revisit the owner's confirmed unrecoverable logs. [Railway logs](https://docs.railway.com/observability/logs)

## Options and tradeoffs

| Option | Coverage and cost drivers | Tradeoff |
| --- | --- | --- |
| **A. stdout/stderr → Vector → Better Stack (proposed)** | Application JSON plus PHP startup/fatal errors and worker process output. Cost: log ingestion/retention, forwarder compute and any persistent buffering. Better Stack publishes a Vector integration and bundled 30-day retention. | Meets the requested process-stream coverage; adds process supervision, buffering and shutdown work. Obtain a quote from measured volume rather than assume a free tier is sufficient. [Integration](https://betterstack.com/docs/logs/vector/), [pricing](https://betterstack.com/pricing) |
| **B. stdout/stderr → Vector or Alloy → Grafana Cloud Logs** | Similar process coverage; cost depends on volume and plan. Grafana advertises 14-day Free and 30-day Pro log retention. | Good if Grafana is already used; introduces Loki label/query conventions. Keep document/job IDs as fields rather than high-cardinality stream labels. [Pricing](https://grafana.com/pricing/) |
| **C. Laravel Monolog/vendor SDK → external intake, plus stderr** | Smallest application-level integration; same remote storage costs, potentially no separate collector service. | Captures Laravel log calls but does not by itself capture arbitrary stdout, pre-bootstrap PHP failures or Horizon console output. Long-lived worker flushing and bounded timeouts need explicit tests. Useful interim application coverage, incomplete for the requested full stream capture. [Railway integration guidance](https://docs.railway.com/guides/third-party-observability) |
| **D. Scheduled Railway CLI/API exports to object storage** | Can archive available deployment logs; storage and scheduler costs. | Polling gaps, pagination, replica/deployment enumeration and rate limits create recovery risk. Cannot recover already-expired logs. Suitable for supplementary archives, not the primary capture path. [Railway CLI logs](https://docs.railway.com/cli/logs) |

Final vendor selection needs expected GB/day, monthly budget, retention and storage-region requirements. No subscription is being purchased in this task.

## Concrete implementation scope after approval

1. **Inventory and separate sources.** Cover every production web and Horizon replica, then staging with distinct source labels and intake credentials. Record the live start commands and deployment metadata before designing process supervision. The current repository has an existing stderr channel; live overrides still need checking.
2. **Emit structured events.** Configure Laravel's stderr channel with a JSON formatter that includes exception stacks; emit each event as one line with escaped newlines. Set PHP runtime errors to stderr. Preserve stdout for non-Laravel process messages. Keep UTC timestamp, severity, message, environment, service, deployment, replica/PID, request ID, job UUID/class/queue/attempt, document ID and SQLSTATE where available. Retain exception class and previous-exception chains while removing credentials, request bodies, document text and SQL bindings. Do not log full database URLs. Add job context cleanup so Horizon does not attach one document's context to the next job.
3. **Capture streams at their source.** Package a pinned forwarder with each application container, or use an explicit local pipe/socket receiver managed by a supervisor. Prototype Vector's streaming `exec` source with stderr inclusion. Capture the actual web/worker process and its children, then fan out sanitized events to Railway's console and external HTTPS intake. A standalone Railway collector cannot automatically read sibling containers' stdout or their Docker socket; if used, each source must explicitly send to it. Test child exit codes, signal forwarding, readiness and graceful Horizon shutdown before choosing the wrapper. [Vector exec](https://vector.dev/docs/reference/configuration/sources/exec/)
4. **Make buffering and loss behavior explicit.** Batch HTTPS delivery; configure retries and bounded queues. Use a persistent spool where the Railway service topology supports it, or send acknowledged batches to a separate collector with a persistent volume. An ephemeral container buffer can lose undelivered events on replacement, even though already-ingested vendor logs survive. Validate volume/replica support before choosing spool placement. Set a documented outage capacity from measured bytes/sec; alert before exhaustion. Choose and test the backpressure/drop policy rather than silently blocking document jobs indefinitely. Vector supports HTTP sink disk buffering, but end-to-end durability depends on the source and volume lifecycle too. [Vector HTTP sink](https://vector.dev/docs/reference/configuration/sinks/http/)
5. **Retain and monitor.** Provision the chosen retention explicitly, with separate production/staging sources. Set ingestion/buffer failure and missing-heartbeat alerts, plus failed-job and SQLSTATE error searches. Send a small per-service heartbeat so a broken drain is visible even when the application is quiet. Add an export procedure for incident bundles containing a UTC window and all replicas. Scope coverage to application/process logs; PostgreSQL server logs need their own provider integration and cannot be manufactured by an application drain.
6. **Stage, review, then deploy.** Prepare a reviewable change covering logging formatter/context, forwarder config, service entrypoint, secret names, dashboards, rollback steps and cost estimate. Validate in staging first. Present the actual changes and evidence for production approval. Rebuild config cache and restart workers as part of the approved rollout so every process uses the new logging configuration. Keep the direct database endpoint throughout.

## Acceptance evidence required before closing Tier 1

- Emit unique synthetic web and queued-job events, a handled exception with a previous exception, and a PHP stderr message. Confirm exact class, SQLSTATE, stack, job/attempt and deployment identity in the external store.
- Emit before and after a staging redeploy and worker restart; verify all markers remain searchable externally after the original container is gone. Do not infer durability merely from Railway's live log view.
- Run a controlled concurrent-job burst and reconcile expected/received event IDs across replicas. Check sequence and duplicate behavior, multiline stacks, redaction and largest expected exception size. Do not use real customer documents for the canary.
- Interrupt external intake, then restore it: verify retries, buffer recovery and documented loss limits. Restart/redeploy the collector with pending data to prove the chosen persistent buffer survives. Verify job latency and exit behavior remain acceptable during the outage.
- Confirm retention settings and revisit a dated canary beyond Railway's retention horizon. Record the configured-retention check separately from this later elapsed-time check.
- Confirm alerts detect a disabled drain and that logging failure does not recurse through the same failed sink.

Rollback removes the new forwarding wrapper/channel while preserving remote records and stderr output. Export incident evidence before deleting or changing retention on any external source. The eventual production pooling decision is independent of this logging rollout.
