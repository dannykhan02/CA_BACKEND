# DocIntel deterministic hardening — phase 1 audit

**Scope and evidence.** Static, repository-only audit of `CA_BACKEND` at `3082b4b` (`main`), 2026-10-11. No provider, database, production, or runtime calls were made. Findings describe code paths, not measured production incidence. Paths below are relative to repository root. A proposed rule is a recommendation, not an implemented control.

**Classification:** A adequate deterministic control; B deterministic but fragmented; C safe, high-value implementation candidate; D configuration; E upstream schema or extraction change; F document-dependent AI judgment; G not a current problem. **Priority:** P0 correctness, security, or cost exposure; P1 important reliability or coverage; P2 useful hardening; P3 optional. A row has one primary classification; related dependencies appear in the proposal. “False rejection” is the expected recall cost if the rule is implemented conservatively.

## 1. Top P0 findings

1. **Structural and field-role proof is missing.** A cited span proves presence and locality, not that a table cell belongs to a particular row/column/title or that each extracted field came from its rightful source fragment. This is the highest-value upstream contract change; do not compensate with wider quote windows.
2. **Typed relations are incomplete across layers.** Percentage basis, percentage points, basis points, rates/per-unit values, ranges and qualifiers need one typed compatibility owner. B2 contains useful local guards, but B1 and parser semantics are not identical.
3. **Assertion force and conflict handling need explicit state.** Number grounding does not establish “shall” versus “may,” exception scope or original versus restated status. Conflicting values currently coexist without a conflict/supersession relation.
4. **Untrusted and hostile input boundaries need enforcement.** Prompt instructions and B2’s reduced context help. The common Anthropic path only warns on an unapproved model; XLSX/PDF parser resource limits and optional malware scanning are uneven. Document content must never set provider policy or authorize actions.
5. **Cache and terminal-work invariants need a single policy.** B2 identity omits a semantic-policy fingerprint. Stage status checks are spread across jobs, so prerequisite failure and late dispatch need a transition audit. Existing checkpoints and B1 fallback materially reduce risk.
6. **Privacy provenance of checked-in evaluation artifacts is unresolved.** Tracked raw-response and extracted-text files require an ownership/consent inventory; this is an audit finding, not a claim that those files contain production customer data.

## 2. Top P1 findings

- Add a deterministic candidate worklist and coverage telemetry for explicit figures, percentages, dates, section headings, table rows, deadlines and obligation cues. Candidates trigger inspection only.
- Make numeric locale, fiscal calendar, OCR channel and physical-unit uncertainty explicit before accepting more formats.
- Preserve current density-aware routing; add parser preflight and predictive OCR/visual limits before spending.
- Separate boot readiness, processing readiness and optional provider readiness.
- Keep billing amounts, model identity, budgets, timeouts, feature flags and display counts configured and validated.

## 3. Protections already implemented and needing no redesign

- Span IDs resolve to original extracted text, require extraction version and supplied chunk membership, and bound count/locality. Raw source text is not rewritten for B2.
- B2 verifier version is `3`; per-number cited-record binding exists; B1 top-six controls prominence, not B2 eligibility. B2 uses up to `b2.max_records` and token budget, so eligible evidence may still be omitted with coverage reported.
- `max_rejected_claims = 0`; a rejected or unavailable B2 returns B1. Brief reads do not invoke a provider. B2 verified results are reused only for a matching input hash.
- Explicit dates are checked against cited source; ambiguous slash dates are not guessed; relative dates retain an unresolved anchor.
- Negative/absence claims face dedicated guards and coverage checks. The only implemented derived numeric operation seen in Brief verification is explicit `growth_percent` with comparable cited inputs; general arithmetic is not admitted.
- Document and Matter API reads shown here apply policy or scoped lookup; credit operations use locks and idempotent reserve/settle/release. The current architecture should be extended selectively, not rewritten for terminology.

## 5. Work that remains AI and document-dependent

Extraction of meaning, subject/action/object links, synthesis, explanation, relevance and materiality judgments when evidence is ambiguous remain model-assisted. Deterministic validators must check the resulting schema, semantics and provenance. No rule should encode particular organizations, programs, report types or layouts as knowledge.

## 6. Required Stage A/schema/extraction changes

1. Structural provenance graph: cell, row header, column header, title, footnote, caption, section/list parent and explicit page continuation, all bounded to source offsets and version.
2. Field-role links: source support for subject, metric, value, unit/currency, period, denominator/basis, entity, action/object and assertion qualifier on one record.
3. Typed relation data: physical dimension, numerator/denominator, percent basis/delta, bound/range, precision, sign and duration anchor.
4. Conflict/supersession: stable metric/entity/period identity, edition/channel, conflict state and explicit amended/restated relation.
5. Locale/channel/quality metadata: number format, language, fiscal calendar, native text versus OCR, factual glyph uncertainty, and coverage/candidate state. Each addition needs a migration plan that leaves old evidence `unknown`, not silently upgraded.

## 7. Values that belong in configuration

Prices, credit allowances and confirmation bands; B1 top-six and other display counts; model IDs and approved task models; context/output tokens; timeouts; retry and split limits; page/image/ZIP/cell resource ceilings; evidence count/locality; document/call/job spend ceilings; retention periods; feature flags and provider settings. Validate cross-field safety constraints at startup or feature admission. Semantic alias tables may be code/data with a policy fingerprint; their **meaning** must not drift through mutable business configuration.

## 8. Proposed implementation sequence and evaluation gates

1. **Boundary and cost, no schema:** enforce task model/price admission, parser resource preflight, terminal transition checks and provider-free reads; inventory/redact evaluation artifacts. Safety: unauthorized/over-budget provider calls, parser exhaustion, leaked raw content, late dependent dispatch. Usefulness: supported files/jobs accepted and completed; legitimate calls not refused.
2. **Semantic core:** central matching-only normalizer and typed compatibility service; distinguish percent/points/basis, duration, currency, per-unit, qualifiers, signs and declared rounding. Add B2 semantic-policy fingerprint only for interpretation changes. Safety: wrong-unit/basis/qualifier/precision admissions and stale verified cache reuse. Usefulness: supported same-unit paraphrases and exact scale conversions accepted.
3. **Upstream provenance:** bounded table/heading/list graph, field-role citations, OCR/locale metadata, conflict and assertion force. Admit only evidence whose required links validate. Safety: wrong row/column/entity/period, force reversal and silent conflict winner. Usefulness: valid multi-part table facts and qualified claims recovered without cross-record borrowing.
4. **Coverage and product contracts:** candidate worklist with inspected/missed status, conflict/quality API fields and separate persistent user-note anchors. Safety: unsupported candidate promotion and annotation-as-evidence. Usefulness: supported extraction recall, stable highlights and clear quality reasons.

For each phase, use paired fixtures including the adversarial examples in this brief and real authorized documents. Report **unsafe/unsupported admission rate** and **supported rejection/false-refusal rate** separately, stratified by native/OCR, table/prose, language, locale and document size. A stricter rule ships only with a measured recall cost and an explicit uncertain/review path.
