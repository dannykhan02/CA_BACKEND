## Scheduler reconstruction

`IncrementalPipeline::start()` plans all roots in one transaction. `pump()` locks the document and dispatches at most `DOCINTEL_EXTRACTION_CONCURRENCY` queued plus running extraction chunks, default **2**. Every completion, split, retry, recovery, or budget deferral calls `pump()` again. Split children enter the same pending window. Merge is eligible only when every extraction leaf is terminal; a split parent is excluded from failure counting. Pending or queued children keep merge ineligible.

An extraction worker starts `ProcessDocumentChunkJob`, obtains a Redis `ProviderGate` lease, counts tokens, claims the chunk under the document row lock, reserves cost, sends one extraction request, settles cost, and pumps. The gate's global cap is **2** leases across processes, replicas, and web requests. Its per-document cap is **2**. Production Horizon config starts **2 extraction processes per replica**. A read-only allowlisted Railway variable check found `APP_ENV=production` and no overrides for `HORIZON_EXTRACTION_MAX_PROCESSES`, `ANTHROPIC_MAX_INFLIGHT`, or `DOCINTEL_EXTRACTION_CONCURRENCY`, so those code defaults apply; the live replica count and process health were not available. One lease currently covers the whole chunk job, including count-token and local bookkeeping, and is released in `finally`. A crashed holder expires after **240 s**; expired leases are purged atomically on the next acquire. A release failure can temporarily leave a lease until expiry. `stats()` alone does not purge it. The Redis queue visibility window is **390 s**.

Before this change, `otherDocumentsQueued()` treated *any* queued extraction row from another document as a reason to reserve the last free global permit. With global cap 2 and one permit already held by the same document, that denies its second chunk as `fairness`, even if the other row has no worker or is stale. The denied job is cloned into a delayed Redis message after **15–30 s** (15 s base plus 0–15 s jitter), returns to the queue tail, and may repeat. A real denied document is registered in the gate's waiting set for **60 s**, and the gate still reserves the last permit for that waiting document. Synthesis priority claims are also retained across delayed redelivery. The change removes the database-row proxy from chunk admission; actual gate waiters preserve multi-document fairness while spare capacity is usable.

`queue_wait_ms` was measured from original dispatch to *successful chunk claim*. It therefore combines first worker wait, every scheduled deferral, post-delay worker wait, other queue backlog, and retry history. It is not a Redis queue-time metric. New `cost_accounting.queue_timing` metadata records initial and post-delay `worker_wait_ms`, scheduled `fairness_wait_ms`, scheduled `provider_admission_wait_ms`, and deferral count. It retains the original dispatch token and resets on a new dispatch. The report keeps the legacy aggregate and reports the components separately; old runs have `null` component totals. The component counters are sums across chunks, not wall-clock intervals, and do not include time spent doing local work before the provider request.

## The 342,292 ms sector-report wait

The 342 ms quota rejection occurred *after* the chunk finally reached admission. Thus virtually all of its 342,292 ms `queue_wait_ms` preceded that provider response. The aggregate alone cannot distinguish actual ready-queue backlog, repeated 15–30 s fairness/global deferrals, worker shortage, or a mixture. In particular, 342,292 ms is close to the full 5 m 42 s incremental phase because the chunk appears to have been dispatched near its start and admitted near its end. This is compatible with the old one-slot fairness behavior, but does not prove it was the reason for this chunk. No stale lease can be established from the supplied data. The next controlled run's component counters and gate denial logs can answer this exactly.

## Effective concurrency and splits

The configured extraction ceiling is min(global 2, per-document 2, available extraction workers), with **2 configured workers per replica**. The old eager fairness check can reduce a document to **1** while any other document has a queued extraction row. The ADB provider sum was 1,003 s across an incremental phase of 988 s. The sector sum was 328 s across 342 s. These totals suggest near-serial service, but exact average and peak concurrency require each request's start and finish. `docintel:pipeline-report --json` now reconstructs those intervals from completion timestamp minus recorded transport duration and reports average, peak, and percent of provider wall interval at concurrency 1 and 2+. Historical timestamps have second-level storage precision and older extraction durations included local validation, so old overlap estimates have corresponding error.

ADB: 5 roots, 3 split parents, 11 final leaves, 18 extraction calls. The tree contains 14 nodes, so the split parents generated 9 children in total; at least some split created more than two children. Four calls exceed one attempt per tree node and must be retries, continuations, or other repeat extraction attempts. The specific categories cannot be identified without run rows. Split reasons are limited by code to `max_tokens`, `context_overflow`, and `timeout`; their actual distribution is unknown. A split parent without salvaged records contributes no final leaf evidence. Its provider duration, input/output tokens, and cost are now separately reported, together with each parent's failure class and immediate child calls/cost. Exact ADB wasted values were not in the supplied aggregates and must remain unknown.

## Root-planning sensitivity

The planner uses model input capacity, 16,000 output-token cap, 75% planned fill (12,000 tokens), 150 output tokens per predicted record, a record rate of 4/1,000 source tokens (6 for detected dense content), labeled-span byte weights, and 400-token maximum cross-boundary overlap. The resulting request limit is about 79 records. ADB's 77,000 source tokens across five roots averaged 15,400 before overlap; its 85,911 generated output tokens include work later discarded or continued, so dividing that total by roots overstates useful output per root. `max_records` is a ceiling per call, not a guarantee of full coverage; saturation is reported.

An extra root costs one request's fixed prompt and overlap but may save multiple failed parent and child requests. No root-size change is made before that evidence exists.

## Two-minute calls and output volume

Incremental extraction sets Laravel HTTP timeout **120 s**, connect timeout **10 s**, one HTTP attempt per chunk, chunk job timeout **180 s**, extraction Horizon worker timeout **360 s**, and Redis `retry_after` **390 s**. Token-count requests use **15 s** and **5 s** connect timeout. Thus calls failing near exactly 120 s with `timeout` / cURL 28 are consistent with the HTTP client limit, not Horizon or Redis. Without individual stop reasons and failure classes, a natural model response near 120 s cannot be ruled out. The repository has no Railway process timeout setting. Timeout values were not increased.

Span mode removes evidence quotes, but each structured record still includes label, value, subject, reference, evidence IDs, kind, confidence, aliases, and ten nullable metadata fields. Empty and null fields repeat at scale. Label, value, subject and typed metadata carry product meaning; evidence IDs and date fields are essential to grounding and correctness. Removing schema fields or shortening values would change validation or coverage, so no output-shape change is included.

## Changes, expected impact, and retest

Ranked latency drivers from the available evidence are: (1) long per-request inference, around 63 s median on both runs; (2) the eager fairness rule, which can idle the second global slot and impose repeated 15–30 s delays; (3) reactive split and repeat calls, which account for 13 of ADB's 18 calls beyond the five roots; (4) the two-job document window and actual worker availability, which can compound the gate wait; and (5) structured-output volume, 85,911 ADB tokens. Only the first, third, and fifth have observed run totals. The specific contribution of the second and fourth to the historical 342 s wait remains unmeasured.

The change lets a document use its second existing permit when no other document has actually registered for admission; global and per-document caps stay at 2, and registered waiters retain fairness. This can remove repeated 15–30 s deferrals and permit nearly 2× extraction throughput when two workers and provider capacity are free. The gain is zero when global capacity is truly occupied, only one worker is available, or output generation itself dominates. Provider cost should be unchanged for the same call tree; faster admission could expose existing document-budget reservations concurrently, but the locked budget check remains. The report now exposes per-request intervals, split-parent waste, and queue components without storing source contents. No environment or production configuration change is required for the code change. The actual production worker count and quota still need verification before performance measurement.
