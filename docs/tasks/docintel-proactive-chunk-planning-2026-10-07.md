# DocIntel proactive chunk planning — 2026-10-07

## Current decision model

`IncrementalPipeline::route()` counts whole-document tokens with Anthropic's free count endpoint when the byte bound exceeds `large_tokens`; failure uses a one-token-per-three-byte estimate. `ExtractionCapacity::decide()` uses the configured extraction model's context and output caps, the prompt/schema byte bound, 10% context reserve, a 75% output fill target, 150 output tokens per predicted record, and 4 expected records per 1,000 input tokens (6 when the *whole document* is classified dense). The configured extraction output cap is 16,000, giving a 12,000-token planned output target and a 79-record request limit. `max_records` in the actual extraction request is that limit, not 99,999; the job's 99,999 envelope value is used for conservative reservation sizing. The planner makes the fewest balanced root partitions within the resulting token target. Span mode partitions at complete evidence-span boundaries, with up to 400 tokens of whole-span overlap; legacy mode prefers headings, pages, blocks, sentences, then whitespace. There is no per-root output-risk estimate or historical-performance input in the old planner.

Each admitted chunk is token-counted. Input above the request bound fails `context_overflow`. `max_tokens`, `context_overflow`, and `timeout` can reactively split; other validation/provider failures cannot. Reactive splitting halves estimated size and creates span-aligned or semantic children. Minimum size is 2,000 characters per child, maximum depth is 2, and the total split-parent budget is two per root. `max_tokens` with validated partial output follows the separate salvage/continuation path. A returned response with `stop_reason=max_tokens` raises structured truncation; an output reaching `recordLimit()` marks saturation. No validation, evidence-ID, date, model, credit, or concurrency rule was changed here.

## New rule and split behavior

The preflight uses the already-counted input tokens, source-only density, evidence-span types (or the same local segmenter in legacy mode), table rows and list items. Estimated records are the larger of `ceil(input_tokens / 1000 × configured prose/dense record rate)` and `ceil(1.5 × table_rows + 0.5 × list_items)`. Estimated output is `records × 150 + 64` tokens. A root is proactively split only when it is at least twice the existing minimum child size and either output exceeds the existing 12,000-token safe output target, or a structurally dense root (at least 12 table rows or 30 list items) reaches 90% of that target. A successful provider token count is required. These thresholds use existing configured output capacity; no model or provider setting changes.

The proactive split makes exactly two non-overlapping children. In span mode it cuts only at a span start and keeps existing evidence IDs/version. In legacy mode it chooses a heading, page, paragraph/block, or sentence boundary inside the feasible minimum-size range. If no safe boundary exists, the normal provider path remains available. Only depth-zero roots use this preflight, so proactive recursion cannot explode; existing reactive splitting remains the fallback. Proactive parents have no extraction attempt or cost reservation and are tagged `split_kind=proactive`.

## Completeness and latency interpretation

`EvidenceBudget::forDocument()` excludes split parents and assesses final leaves, dropped records, saturated leaves, unresolved references, and synthesis evidence trimming. `GenerateDocumentSummaryJob` also considers optional synthesis items and non-split failed chunks. A recovered timeout alone should not make Ready become Partial; the code already excludes split parents. The supplied 680 returned versus 612 accepted implies 68 rejected records, which may explain Partial via `dropped_records`, but the exact persisted coverage reason was not supplied. The report now shows the persisted coverage components and keeps historical failed attempts separate. No completeness rule was loosened.

Avoiding two 120-second parent attempts would remove about **240 seconds of summed provider work** and two extraction requests if the same nine leaves suffice. The extraction sum would fall from 15m48s to about 11m48s in that counterfactual. Wall-clock saving is not 240 seconds by default: the calls overlapped other work. Dividing by observed effective parallelism 1.79 gives a rough **134-second scheduling proxy**, subject to critical-path placement, child duration, and queue effects. Theoretical wall saving ranges from little or none to roughly four minutes if both parents blocked the critical path sequentially. The measured 9m44s total is not a guaranteed future runtime. Two failed calls were unpriced, so actual USD saved cannot be quantified; avoiding them removes their provider work and duplicated parent input context, with no change to the nine useful leaf requests in the simple counterfactual.

## Observability and limits

Each new extraction run's UUID is its `provider_attempt_id`. Run rows now hold dispatch/worker/admission/lease/provider timestamps, counted and actual tokens, response receipt, timeout source, stop reason, attempt number, and dispatch reason; the report joins chunk key/depth/split kind and marks discarded split-parent output. Timings are per attempt, while old queue counters are per chunk and may combine deferrals. Run `estimated_cost_usd` is available only when usage exists; failed calls may remain unpriced. A split parent's cumulative `reserved_cost` gives DocIntel's settled accounting amount after settlement, but it is not proof of the provider's actual charge when usage is unknown. Settled per-attempt cost is not stored separately by the existing billing path, so the report does not fabricate it. Proactive savings remain null until comparable data exists. No prompts, document text, evidence contents, or secrets enter these metadata fields.
