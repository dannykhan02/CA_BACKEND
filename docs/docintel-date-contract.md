# DocIntel incremental extraction date contract

## Flow

`EvidenceSchema::extraction()` supplies the Anthropic structured-output shape for each record. Span mode supplies `evidence_ids`; legacy mode supplies `quote`. The schema requires every field to be present, but nullable fields may be `null`. `date_type` is a nullable scalar enum: `explicit`, `relative`, `inferred`, or `null`. [Anthropic's structured-output schema](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) supports scalar enums with `null`; the schema does not use unsupported array constraints such as `maxItems`. Conditional rules by `kind` remain in application validation.

`EvidenceSchema::instructions()` gives the model the semantic rules. Only the span prompt was revised for this change. A complete calendar date may be normalized to `YYYY-MM-DD`; a partial period stays in `period` without a `due_date`; a relative deadline or obligation keeps its timing expression in `value`. `inferred` is for an inferred deadline or obligation where the existing product contract allows one.

`EvidenceSchema::validate()` checks required fields and types, confidence and label, then grounds the record. In span mode, `ground()` checks extraction version, known in-chunk IDs, count, locality, and nonempty resolved text; it supplies `evidence`, `evidence_ids`, and a compatibility `quote` from the exact source spans. In legacy mode the supplied quote must be a verbatim substring of the chunk. The date check then runs against this grounded quote. Explicit `due_date` must be a real `YYYY-MM-DD` calendar date supported by a complete date in the quote. Recognized source forms are year-month-day, day-month-name-year, month-name-day-year, and unambiguous day/month/year when the day exceeds twelve. An ambiguous numeric source date is not enough to assert one normalized date.

The allowed extraction kinds are `entity`, `metric`, `deadline`, `obligation`, `risk`, `fact`, `definition`, and `unresolved`. All kinds carry the nullable date fields because they share one provider record schema. For `deadline` and `obligation`, a non-null `date_type` from `explicit`, `relative`, or `inferred` is mandatory. Invalid date semantics reject the record. For all other kinds, date metadata is optional: safe inconsistencies are cleared without changing `kind`, `label`, `value`, `period`, or evidence. Unsupported date types, malformed dates, and calendar-invalid dates still reject the record for every kind.

`period` is faithful source period text, especially for metrics. It may be a month and year, fiscal year, quarter, or year; it never supplies missing components for `due_date`. `value` is the observation or factual statement and is not rewritten during date salvage. For relative deadlines and obligations, `value` is also the current carrier for the relative timing expression. There is no separate relative or inferred date field in the extraction schema. `due_date` is only for explicit complete dates and is otherwise `null`. An inferred deadline or obligation has `due_date=null`.

Validated records are checkpointed in `document_chunks.result`. `EvidenceMerger` reads only kept records. It persists the record and sources in `document_evidence`; metric identity and derived `document_kpis.period` use `period`. Deadline and obligation records create `document_deadlines` with `date_type`, nullable `due_date`, and `relative_text` from `value` when there is no due date. No merge or database schema change was needed. The existing API, frontend, and report exports already accept nullable due dates and display `relative_text` for deadline-like rows; noncritical date metadata is not required by those consumers.

## Sanitization and diagnostics

For kinds other than deadline and obligation, `explicit` with no `due_date` becomes `date_type=null`; a `due_date` paired with a non-explicit type is removed; a well-formed explicit date absent from the grounded quote has both date fields removed. `period` and core fields remain intact. When a nonempty period survives one of these changes, diagnostics count `partial_period_preserved`. No date is inferred or fabricated.

Chunk diagnostics contain `records_date_metadata_sanitized`, `date_metadata_sanitized`, `date_rejection_reasons_by_kind`, and `date_metadata_sanitized_by_kind`. These are aggregate counts keyed only by stable reason and finding kind. The validation report aggregates them under `date_handling` while retaining its existing fields. Historical chunks without these keys still contribute their rejection counts, but have no historical kind breakdown. Neither diagnostics nor logs store source or evidence text.
