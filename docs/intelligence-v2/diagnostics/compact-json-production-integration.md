## Transport, mapping, and drift guards

`DOCINTEL_EXTRACTION_WIRE_FORMAT` selects `canonical-json-span-v1` (default) or `compact-json-v1`. `IncrementalPipeline::start` snapshots the selected mode in `documents.ai_pipeline.extraction_wire_format` once per document pipeline. Existing runs keep that value when the global config changes; new pipelines can use the new value. Legacy quote grounding remains canonical. No Stage A, B1, or B2 consumer receives compact keys.

`CompactEvidenceExpander` builds its provider schema from `EvidenceSchema::extraction(span_reference)`, using one bijective key mapping and canonical rules. It checks the entire canonical provider schema hash and the frozen Control prompt hash before producing a schema or expanding data. This catches added fields, changed requiredness/nullability, changed field descriptions, changed enums, or changed prompt semantics until the codec is explicitly reviewed and versioned. The compact schema is generated from code; the JSON artifact is a review snapshot checked by the unit test.

Expansion rejects unknown keys, missing required fields, null supplied for an omitted-null field, wrong types, invalid enums, and wrong array shape. It fills **only** an absent canonical nullable field with `null`. It preserves literal values and order. The expanded object enters unchanged `EvidenceSchema::validate`, grounding, provenance, typed projection, and downstream processing. Continuation context reads validated canonical records from the prior chunk result.

For `max_tokens`, a separate compact scanner reads the `m` array from its beginning and returns only a contiguous prefix of complete JSON objects that strictly expand. It stops at the first incomplete, malformed, or unexpandable object. It does not repair delimiters or values. Canonical validation still runs on the expanded prefix. The raw truncated provider text remains in the AI run audit row.
